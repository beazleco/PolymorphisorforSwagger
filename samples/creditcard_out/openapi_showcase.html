What each disposition means

Published An SOR field backs this element on every variant of the operation, so it is published.
Variant only Backed by the SOR on some variants of this operation and not others, so it appears only in those variants.
Not in the SOR The workbook named an SOR field, but no element of that name exists in the message of the SOR endpoint this sheet points at. It is removed.
No SOR field The SOR column is empty, so the workbook says the System of Record does not supply this element. It is removed.
Container A group rather than an element. It is published only where something beneath it is.

How this was decided

For every row of every operation sheet the tool asked, in order:

  1. Does the workbook name an SOR field for this element? An empty SOR cell is the analyst saying the System of Record does not supply it, and the element is removed.
  2. Does that field exist in the System of Record? The sheet names an SOR endpoint, on the SOR API Endpoint banner cell or on the SOR column header. A Request Body row is looked up in that endpoint's request, meaning its body for POST and PUT or its parameters for GET, and a Response Body row in its response. Matching is on the last segment of the field name, so accountInfo.currency resolves to any element named currency. A field that is not there means the element is removed, and the removal is listed against its cell.
  3. Do all variants of the operation supply it? Where an operation is served by several SOR endpoints, an element supplied by some and not others appears only in those, through allOf inheritance from a shared base.
  4. Do other endpoints share this class? A class used by more than one endpoint with different content is split, so no endpoint is shown another endpoint's elements.

The banner and the column header are required to agree about which SOR endpoint applies. Where they disagree the operation is not generated, because verifying against the wrong endpoint would be worse than not verifying at all.
